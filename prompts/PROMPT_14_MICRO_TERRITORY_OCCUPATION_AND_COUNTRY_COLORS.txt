# PROMPT 14 — 미세 영토, 일부 점령, 국가 색상

이 문서는 현재 저장소에 Prompt 14를 구현하기 위한 실행 프롬프트다. 구현자는 아래 단계를 순서대로 수행하되 각 checkpoint에서 중단하고 다시 시작할 수 있어야 한다. 한 번의 실행에서 전체 작업을 끝내려고 검증이나 차단 조건을 생략하지 않는다.

Prompt 10~13에서 완성된 command, planner, atomic world+simulation commit, history, undo/redo, turn resolution, UI, MapLibre incremental update 구조를 보존한다. 문서와 실제 저장소가 다르면 실제 코드와 데이터가 권위 원본이다. 차이를 audit 보고서에 기록하고 기존 구조를 우회하는 병렬 구현을 만들지 않는다.

---

## 1. 목표와 범위

### 1.1 구현 목표

1. 세계를 안정적인 미세 `TerritoryId` 집합으로 표현하는 immutable geometry catalog를 오프라인에서 생성한다.
2. 런타임 polygon 분할 없이 기존 territory ID 집합을 사용해 일부 영토의 점령·해방·양도를 처리한다.
3. 법적 소유자인 `ownerCountryId`와 실제 지배자인 `controllerCountryId`를 분리한다.
4. `CountryEntity.mapColor`를 국가 색상의 authoritative world state로 둔다.
5. 모든 변경을 `command → validation → planner → atomic commit → projection → history → undo/redo` 경로로 처리한다.
6. immutable geometry/topology/render catalog와 mutable world/simulation state를 분리한다.
7. 동일한 입력과 도구 버전에서 stable ID와 byte-identical asset을 생성한다.
8. 실제 행정구역 polygon 원본의 release/version, license, attribution, hash를 고정한다.
9. 영토와 색상 변경 시 affected feature만 기존 incremental adapter로 갱신한다.
10. GPT는 좌표나 polygon을 생성하지 않고 검증된 territory ID, region reference, country ID만 제안한다.
11. 브라우저 새로고침이나 개발 서버 재시작 시 2020-01-01 canonical seed에서 시작한다. 브라우저 persistence는 추가하지 않는다.
12. 기존 국가 선택, 게임 UI, turn 진행, 뉴스, 주요 사건, 지도 상호작용, history, undo/redo에 회귀를 만들지 않는다.

### 1.2 이번 범위에서 제외

- 역사 시대별 경계 pack의 실제 제작
- 전쟁, 정치, 경제, 외교 시스템의 신규 구현
- GPT가 임의 좌표·선·polygon을 생성하는 기능
- 런타임 Voronoi, grid, polygon cutting 또는 topology 재구축
- 브라우저가 전 세계 canonical GeoJSON을 내려받아 재검증하는 구조
- 백엔드 저장 서버와 브라우저 영속 저장
- raster tile을 점령 판정의 authoritative geometry로 사용하는 구조

역사 경계는 향후 별도 catalog version과 명시적 migration으로 추가할 수 있다는 짧은 호환 원칙만 남긴다. 아직 존재하지 않는 역사 pack schema나 미래 도메인 상태를 미리 구현하지 않는다.

## 2. 현재 저장소에서 반드시 지킬 사실

구현 시작 시 다시 확인하되 다음을 기본 전제로 사용한다.

- 현재 `WorldStateV2`는 mutable territory geometry와 topology를 직접 보유한다.
- 현재 `SimulationStateV1`은 strict schema이며 `playerCountryId`, `queuedActions`, `factsById/factOrder`, `situationsById/situationOrder`, `scheduledConsequences`, `eventLog`, `history`를 가진다.
- world와 simulation은 turn commit, undo, redo에서 한 쌍으로 snapshot·restore된다.
- command batch에는 기존 상한이 있다. 상한을 늘리거나 territory 하나당 command/effect 하나를 만드는 방식으로 우회하지 않는다.
- 지도에는 `updateData` 기반 incremental source adapter가 있다. 초기 적재와 source 재생성에서만 `setData`를 허용한다.
- 현재 전 세계 ADM1 파일이 polygon인지 먼저 확인해야 한다. boundary line은 polygon source가 아니다.
- 현재 중국·미국용 polygon fixture가 존재하더라도 전 세계 production source로 간주하지 않는다.
- 현재 package와 CI에 vector tile generator가 설치되어 있다고 가정하지 않는다.

## 3. 공통 불변식

### 3.1 식별자와 정렬

- `CountryId`는 기존 3글자 canonical ID 계약을 유지한다.
- `TerritoryId`, `EdgeId`, authority ID는 길이 제한이 있는 ASCII canonical ID다.
- 모든 `ById` record와 대응 `Order` 배열은 정확히 같은 key 집합을 가져야 한다.
- `Order`는 locale에 의존하지 않는 bytewise 비교로 정렬한다.
- 중복, 누락, prototype key, 비정규 ID, 예상 밖 필드는 strict validation에서 거부한다.

### 3.2 immutable catalog와 mutable state

immutable catalog가 소유하는 값:

- territory polygon과 bbox/centroid/면적 같은 파생 geometry metadata
- edge와 adjacency
- render feature mapping
- source provenance와 catalog roots

mutable world state가 소유하는 값:

- territory의 owner/controller
- 활성·퇴역 국가와 국가 표시 속성
- `CountryEntity.mapColor`
- revision과 게임 중 변경되는 관계

mutable state는 polygon 좌표를 복제하지 않는다. catalog version/root를 가리키는 ref만 보유한다.

### 3.3 원자성

- world와 simulation 변경은 하나의 plan과 하나의 atomic commit으로 적용한다.
- 부분 성공은 허용하지 않는다.
- stale revision, 잘못된 ID, cap 초과, 권한 부족, invariant 위반은 commit 전에 거부한다.
- undo/redo는 world state, simulation state, catalog ref를 일관된 한 쌍으로 복원한다.
- immutable catalog asset 자체는 undo snapshot에 복제하지 않는다.

### 3.4 공통 debug 정책

debug directive는 production narrative·authority 존재 조건만 우회할 수 있다. 다음 검증은 절대 우회할 수 없다.

- strict schema와 ID 존재 여부
- active/retired country 상태
- canonical color
- owner/controller invariant
- request·batch·collection cap
- stale revision
- atomicity와 deterministic ordering
- catalog version/root 일치

production bundle에서는 debug directive가 작동하지 않아야 한다. occupation, color, merge 등 각 effect는 이 공통 정책을 참조하고 별도 debug 예외를 만들지 않는다.

## 4. 행정 경계 원본과 generation 정책

### 4.1 canonical 기준

- P0는 프로젝트가 고정한 기존 `2020-01-01` 게임 seed의 국가 ID와 canonical owner를 기준으로 한다. 날짜는 게임 시작 기준이며 외부 기관이 증명한 법적 경계 날짜를 뜻하지 않는다. 원본 seed는 보존하고, 새 catalog의 국가 범위 기준은 검증된 별도 게임용 derived P0다.
- 최신 행정구역을 사용하더라도 미세 점령을 위한 operational partition일 뿐 2020 국가 주권을 바꾸지 않는다.
- territory의 `sourceCountryId`는 catalog 생성 당시 canonical 2020 owner다. 현재 게임 owner가 아니다.
- registry/provenance에 `operationalOnly: boolean`을 명시한다.
- 원본 P0는 `boundaryKind: project-game-seed-2020`, 게임용 derived P0는 `project-game-seed-derived-2020`이다. 둘 모두 `operationalOnly=false`다. P1은 `administrative-operational`, `operationalOnly=true`이며 검증된 derived P0 내부를 분할하는 입력이다.
- 사용자 결정에 따라 법적 경계 외부 증명은 필요하지 않다(`legalEvidenceStatus: not-required`). 확보하지 않은 증거를 verified로 표시하거나 이 증명을 위해 추가 자료를 확보하지 않는다.
- 기존 국가 ID, 소유권, 국가 선택, seed 외관을 유지하고 외부 원본→고정 변환 코드·정책→현재 P0 bytes의 재현성을 검증한다.

### 4.2 source lock

각 production polygon source는 최소 다음을 고정한다.

```ts
type BoundarySourceLock = {
  sourceId: string;
  release: string;
  sourceVersion: string;
  license: string;
  attribution: string;
  acquiredFrom: string;
  repositoryPath: string;
  sha256: string;
  byteLength: number;
  geometryTypes: Array<"Polygon" | "MultiPolygon">;
  coveredCountryIds: CountryId[];
  boundaryKind: "project-game-seed-2020" | "administrative-operational";
  operationalOnly: boolean;
};
```

`acquiredFrom`은 재현 가능한 release URL 또는 release 식별자다. floating latest URL에 의존하지 않는다. 네트워크가 필요한 경우 임의 최신 API를 바로 사용하지 말고 고정 release 확보 절차와 라이선스를 먼저 보고한다.

### 4.3 14-2 hard gate

14-2 완료 전에 실제 파일 bytes로 다음을 검증한다.

- production 범위에 필요한 polygon asset이 저장소 또는 재현 가능한 build input으로 존재한다.
- geometry가 `Polygon`/`MultiPolygon`이고 유효하다.
- 중국·미국 외 여러 대륙의 국가를 포함한 coverage가 source lock과 일치한다.
- release/version, license, attribution, SHA-256, byte length, repository path가 기록된다.
- 국가 경계와 미세 행정구역의 containment/coverage 정책이 검증 가능하다.
- metadata 국가 집합, 선택 geometry 유효성 및 안정적 identity, P0 기준 gap·overlap·cross-border, 선택·제외·fallback 및 P0/P1 lock, atom·vertex cap, source lock과 실제 bytes, 원본·derived·도구 재현성, 두 번의 delivery 일치, 보고서 일치를 모두 검증한다.
- 법적 2020 경계의 외부 증명은 hard gate가 아니다. 이 변경으로 geometry·coverage·재현성·원자성 gate를 우회하지 않는다.
- 고정 외부 원본의 공유 경계를 양쪽 국가가 함께 사용하도록 별도 derived P0를 생성할 수 있다. 원본 source·production seed·metadata bytes는 보존한다. 독립 단순화, 국가 ID 순서의 겹침 차감, 임의 승자 배정은 허용하지 않는다. 버전 고정 정책에 좌표 정밀도, 연산, 연속 경계 변위 한도, 면적 변화 한도, island/hole 보존, 실패 조건을 명시하고 실제 전체 국가를 검증한다. 원본 소유권 분쟁은 기술 오차와 구분하며 근거 없이 해결하지 않는다.
- P1은 derived P0에 결정적으로 clipping/정합할 수 있으나 버전 고정 정책의 좌표 정밀도·면적·경계 변화 한도와 사후 coverage/identity 검증을 통과해야 한다. 여러 P1에 닿는 residual은 실제 공유 행정 경계의 제한된 연장과 polygonization으로 분할을 검토한다. 각 조각의 유일한 원본 연결을 증명하지 못하면 미해결로 남긴다. 중심점·최근접·ID 순서 배분, 임의 filler·grid·Voronoi·균등 분할은 허용하지 않는다.
- 안전한 P1을 사용할 수 없는 국가는 검증된 derived P0 전체를 단일 territory로 사용하는 제한적 fallback을 검토한다. 국가별 원본 P1 수, 선택 territory 수, 유지·제외·정합 identity, 대안 검토, 이유·coverage·cap 영향과 내부 일부 점령 제한을 보고한다. 유효한 분할 원본이 있으면 작은 국가도 활용한다. 국가 누락, 소유권 혼동 또는 인접 국가 침범이 있으면 fallback도 실패한다. cap 회피나 대부분 국가의 단일 fallback으로 완료 처리하지 않는다.
- 미국·중국·한국·영국·프랑스는 실제 유효한 행정구역 기반 복수 territory와 원본 identity를 유지해야 한다. 이 중 한 국가라도 단일 fallback이거나 임의 두 조각으로 축소되면 14-2는 blocked다.
- P1에 없는 섬 때문에 국가 전체의 분할을 버리지 않는다. 고정 Admin0 source identity에 연결된 완전한 독립 P0 component이며 P1과 면적 교차나 양의 길이 경계 접촉이 없을 때만 해당 원본 component를 별도 territory로 유지할 수 있다. component 전체와의 equality, 원본 연결·안정적 ID·coverage·cap을 검증한다. 이는 원본 섬을 보존하는 제한이며 해안 residual을 filler 영토로 만드는 허가가 아니다. 해당 component 내부의 일부 점령 제한을 보고하고, 행정구역 소속을 추측하지 않는다.
- 전체 국가 간 overlap, P0 원본 대비 coverage·연속 경계 변위·island/hole, P0/P1 partition의 gap·overlap·cross-border, 국가·owner·identity, cap을 실제 전체 입력에서 검증한다. fixture 통과만으로 대체하지 않는다. derived P0/P1과 z0~3 delivery를 각각 두 번 독립 생성하여 bytes를 비교하고 원본·정책·generator·artifact의 hash/byte length를 lock한다. 전체 z0~6 delivery와 최종 catalog 검증은 후속 단계의 mandatory gate다.

필수 polygon source가 없으면 14-2를 `blocked`로 기록하고 중단한다. boundary line, 임의 grid, 자동 생성 filler, 국가 polygon의 임의 균등 분할로 성공 처리하지 않는다. 이 단계의 검증용 derived P0/P1 입력은 생성할 수 있으나, 14-6 이후의 최종 catalog atom generation과 production schema cutover로 진행하지 않는다.

### 4.4 protected boundary와 cap 결정 순서

다음 순서를 바꾸지 않는다.

1. source별 국가·행정 단계·geometry coverage를 계산한다.
2. 행정 단계와 region scope 조합별 예상 atom 수와 vertex 수를 계산한다. source feature 수와 정규화된 component atom 후보 수를 구분한다. `canonicalAtomKey`의 component 기준 상한이 cap을 넘으면 낮은 feature 수만으로 pass 처리하지 않는다. locked P0/P1 내부의 결정적 grouping으로 줄일 수 있다는 정책과 증거가 없으면 blocked로 남긴다. 후속 generation에서 최종 수치를 다시 검증한다.
   같은 선택 source feature의 완전한 component 집합을 하나의 MultiPolygon 영토로 관리하는 계획은 허용한다. 서로 다른 P1 identity·국가를 합치거나 connector를 만들지 않는다. 각 component의 원본 연결과 membership bijection, 좌표·hole 보존, protected boundary 침범 0, 독립 재생성 일치를 증명하고 raw 후보 수와 projected 수를 모두 보고한다. 이 계획은 14-6/14-7의 실제 canonical key·catalog·최종 cap 검증을 대체하지 않는다.
3. 전 세계 cap, 국가별 cap, vertex budget 안에 드는 단계와 scope를 선택한다.
4. 선택·제외된 level, region, source와 이유를 policy에 기록한다.
5. 선택 후 P0 국가 경계와 P1 선택 행정 경계를 lock한다.
6. atom을 병합할 때 locked P0/P1 경계를 넘지 않는다.
7. lock 이후 결과가 hard cap을 넘으면 generation을 실패시킨다.
8. policy 선택부터 다시 수행한 후 전체를 재생성한다.

LOD는 화면에 그릴 세부 정도만 바꾼다. authoritative cell 수를 줄이거나 locked boundary를 제거하는 수단으로 사용하지 않는다.

### 4.5 delivery 기술 선택

14-2에서 실제 설치 가능성, Windows 재현성, CI, 산출물 크기와 간단한 측정을 바탕으로 다음 중 하나를 선택한다.

1. 버전이 고정된 외부 CLI vector tile build
2. 저장소 의존성으로 고정한 Node 기반 vector tile generator
3. 성능 동등성이 측정된 viewport-chunked GeoJSON

결정 기록에는 도구와 정확한 버전, 설치·실행 방법, Windows/CI 재현 방법, 입출력 경로, deterministic 검증, license, 실패 시 fallback 또는 `blocked` 정책을 포함한다. 증거 없이 PBF 생성을 전제하지 않는다. 선택한 기술이 준비되지 않았으면 조용히 다른 형식으로 바꾸지 않는다.

## 5. catalog 계약

실제 코드 이름은 저장소 convention에 맞추되 의미는 다음을 만족해야 한다.

```ts
type TerritoryCatalogEntry = {
  id: TerritoryId;
  sourceCountryId: CountryId;
  canonicalAtomKey: string;
  geometryRef: string;
  bbox: [number, number, number, number];
  centroid: [number, number];
  area: number;
  provenanceIds: string[];
};

type BoundaryProvenance = {
  sourceId: string;
  sourceVersion: string;
  sourceFeatureId: string;
  boundaryKind: "project-game-seed-2020" | "project-game-seed-derived-2020" | "administrative-operational";
  operationalOnly: boolean;
};

type CatalogEdge = {
  id: EdgeId;
  leftTerritoryId: TerritoryId;
  rightTerritoryId: TerritoryId | null;
  boundaryClass: "country" | "administrative" | "coast";
};

type WorldGeometryCatalogRef = {
  catalogVersion: string;
  geometryRoot: string;
  topologyRoot: string;
  renderArtifactRoot: string;
  manifestPath: string;
};
```

`canonicalAtomKey`는 atom 생성 전에 source feature identity와 정규화된 component identity로 결정한다. 병합 동률 정렬에 아직 생성되지 않은 `TerritoryId`를 사용하지 않는다.

### 5.1 deterministic generation

- 좌표 정밀도, ring 방향, ring 시작점, MultiPolygon component 순서, property allowlist를 고정한다.
- invalid polygon repair 정책을 고정하고 repair 전후를 보고한다. 조용히 geometry를 버리지 않는다.
- atom과 merge candidate 정렬은 canonical key를 사용한다.
- stable `TerritoryId`는 domain-separated canonical bytes에서 생성한다.
- 동일 입력, source lock, policy, generator version으로 두 번 생성해 manifest와 모든 artifact가 byte-identical인지 확인한다.
- territory는 정확히 한 source country partition에 속해야 하며 locked 국가 경계를 넘지 않는다.
- adjacency는 대칭이고 self-edge와 duplicate edge가 없어야 한다.

build-only canonical GeoJSON은 generator 입력·감사용 intermediate다. 브라우저 asset으로 배포하지 않는다.

### 5.2 canonical hashing 계약

hash 규칙은 이 절 하나만 권위 원본으로 사용한다.

- SHA-256과 명시적 domain prefix를 사용한다.
- UTF-8, 숫자 정규화, bytewise key ordering, 허용 property를 고정한다.
- geometry root, topology root, render artifact root를 분리한다.
- root는 manifest 문자열이 아니라 실제 canonical bytes와 artifact bytes에서 계산한다.
- mutable world/simulation content hash에는 immutable geometry bytes를 포함하지 않고 catalog version/root ref만 포함한다.
- provenance 배열은 `(sourceId, sourceVersion, sourceFeatureId, boundaryKind, operationalOnly)`의 bytewise tuple 순으로 정렬한다.

### 5.3 검증 책임

**build/CI**

- canonical territory 좌표 전체 검증
- geometry/topology root 재계산
- containment, coverage, adjacency, edge 검증
- 모든 render artifact의 hash와 byte length 검증
- 동일 입력의 byte-identical 재생성 검증

**Next 서버 bootstrap 또는 production asset readiness gate**

- 배포 manifest와 `WorldGeometryCatalogRef` 일치 검증
- 필요한 asset의 존재, version, root, byte length 검증
- 실패 시 게임 진입 전에 명확히 차단

**브라우저**

- 서버가 승인한 catalog version/root를 신뢰
- manifest에 등록된 content-addressed 또는 versioned tile/chunk만 요청
- 요청 응답이 선언된 artifact identity와 맞는지 확인
- build-only 전 세계 GeoJSON을 다운로드하거나 전체 재해시하지 않음
- 매 render나 camera event마다 대형 payload를 SHA-256 처리하지 않음

### 5.4 MapLibre feature reference

GeoJSON source에 `sourceLayer`를 전달하지 않는다.

```ts
type RenderFeatureRef =
  | {
      sourceType: "vector";
      sourceId: string;
      sourceLayer: "territories" | "edges";
      featureId: TerritoryId | EdgeId;
    }
  | {
      sourceType: "geojson";
      sourceId: string;
      featureId: TerritoryId | EdgeId;
    };
```

## 6. WorldStateV3와 migration

### 6.1 WorldStateV3

V3의 mutable territory에는 geometry 대신 catalog ID와 게임 상태만 둔다.

```ts
type TerritoryEntityV3 = {
  id: TerritoryId;
  sourceCountryId: CountryId;
  ownerCountryId: CountryId | null;
  controllerCountryId: CountryId | null;
};

type CountryEntityV3 = ExistingCountryEntity & {
  mapColor: string; // canonical #RRGGBB uppercase
};
```

허용 상태:

- owner=active, controller=같은 active country
- owner=active, controller=다른 active country
- owner=null, controller=active country
- owner=null, controller=null

retired 또는 존재하지 않는 country는 owner/controller가 될 수 없다.

### 6.2 territoryOrder와 V2→V3 mapping

`territoryOrder` 필드와 canonical ordering 계약은 유지한다. 값은 새 catalog의 전체 `TerritoryId`를 bytewise 정렬해 재생성한다. V2 territory ID를 V3 order에 그대로 보존하지 않는다.

```ts
type TerritoryMigrationEntry = {
  legacyTerritoryId: string;
  targetTerritoryIds: TerritoryId[];
};
```

mapping 규칙:

- V2의 모든 active territory ID가 정확히 한 entry의 `legacyTerritoryId`로 나타난다.
- 각 `targetTerritoryIds`는 비어 있지 않고 bytewise 정렬되며 중복이 없다.
- V3의 모든 territory ID는 전체 mapping에서 정확히 한 번 나타난다.
- 허용 관계는 legacy territory 하나가 하나 이상의 새 territory로 분할되는 one-to-many다.
- 여러 legacy territory가 같은 V3 territory를 가리키는 many-to-one 또는 many-to-many mapping은 거부한다.
- 누락, duplicate legacy ID, duplicate target ID, unknown target, source-country coverage 불일치는 거부한다.
- target territory는 해당 legacy territory의 canonical 2020 coverage 안에 있어야 한다.
- owner/controller는 mapping의 모든 target에 결정적으로 복제한다.

V3 migration은 catalog가 생성되고 모든 consumer가 catalog ref를 읽을 준비가 된 뒤 수행한다. 임시 catalog나 V2/V3 dual authority를 production에 남기지 않는다.

### 6.3 합병과 국가 정체성

합병을 시작한 기존 국가가 identity를 계승한다.

- 러시아가 소련을 만들면 RUS를 유지한다.
- 오스트리아가 오스트리아-헝가리를 만들면 AUT를 유지한다.
- 헝가리가 만들면 HUN을 유지한다.
- initiator의 `CountryId`와 현재 실제 simulation 필드를 유지하고 이름·영토·색상 등 명시된 값만 바꾼다.
- 흡수된 국가는 기존 retired-country 규칙으로 처리한다.

reference rewrite는 실제 `SimulationState` 필드에만 적용한다.

- `playerCountryId`가 absorbed country면 initiator로 변경
- queued action은 유효하게 rewrite할 수 있으면 rewrite하고 자기 참조나 의미가 깨지면 typed reason으로 취소
- active fact/situation/scheduled consequence는 기존 reference 규칙에 따라 rewrite·dedupe하거나 종료
- historical `eventLog`와 history snapshot은 당시 사실을 보존
- authority는 7.4의 lifecycle 규칙 적용

정치·경제·외교의 가상 slice를 테스트용으로 만들지 않는다. 미래 모듈은 명시적 reference rewrite port를 구현해야 한다는 확장 계약만 둔다.

## 7. SimulationStateV2 authority 계약

일반 GPT 결과가 production에서 영토 또는 국가 색상을 임의 변경하지 못하도록 bounded authority를 authoritative simulation state에 추가한다.

```ts
type TerritorialControlAuthority = {
  id: string; // `tca:<canonical-id>`
  actorCountryId: CountryId;
  targetCountryId: CountryId | null;
  allowedTerritoryIds: TerritoryId[];
  allowedOperations: Array<"occupy" | "liberate" | "transfer">;
  validFrom: string;
  validTo: string | null;
  sourceEventId: string;
};

type CountryPresentationAuthority = {
  id: string; // `cpa:<canonical-id>`
  actorCountryId: CountryId;
  targetCountryId: CountryId;
  allowedMapColors: string[];
  validFrom: string;
  validTo: string | null;
  sourceEventId: string;
};

type SimulationStateV2 = Omit<SimulationStateV1, "schemaVersion"> & {
  schemaVersion: 2;
  territorialControlAuthoritiesById: Record<string, TerritorialControlAuthority>;
  territorialControlAuthorityOrder: string[];
  countryPresentationAuthoritiesById: Record<string, CountryPresentationAuthority>;
  countryPresentationAuthorityOrder: string[];
};
```

### 7.1 strict schema와 caps

- 기존 `simulationIdSchema`의 문자·길이 계약을 재사용하고 각각 `tca:`와 `cpa:` prefix를 강제한다.
- authority ID와 record key는 같아야 한다.
- 각 order는 record key 전체를 bytewise 정렬한 정확한 배열이다.
- territorial authority 최대 256개, authority 하나당 territory 최대 512개다.
- presentation authority 최대 128개, authority 하나당 color 최대 16개다.
- territory와 color 배열도 canonical 정렬·중복 제거 상태가 아니면 거부한다.
- 모든 날짜는 유효한 ISO calendar date다.
- `validTo !== null`이면 `validFrom <= validTo`여야 한다.
- active 판정은 `validFrom <= currentDate`이고 `validTo === null || currentDate <= validTo`다.
- actor/target/source event/territory/color reference가 존재하고 유효해야 한다.

### 7.2 serialization과 hash

- authority collection은 strict parse와 canonical serialization 대상이다.
- `SimulationStateV2` authoritative content hash를 도입하거나 기존 simulation hash 경로가 있으면 확장해 네 collection을 모두 포함한다.
- hash에서 record는 대응 order 순서로 serialize한다.
- world와 simulation의 atomic snapshot, commit, undo, redo에 authority collection을 포함한다.

### 7.3 migration

V1→V2 migration은 네 authority collection을 명시적으로 빈 record/배열로 초기화한다. migration 후 strict V2 parse와 deterministic round trip을 통과해야 한다. production에서 V1과 V2를 동시에 authority로 유지하지 않는다.

### 7.4 lifecycle과 역사 기록

authority collection에는 현재 active 또는 아직 시작되지 않은 bounded 권한만 둔다. 만료·무효화된 authority는 제거하고 그 결과를 기존 `eventLog`에 typed lifecycle event로 남긴다. 역사 event를 active authority로 재사용하지 않는다.

- 날짜가 `validTo`를 지나면 제거하고 expiry event 기록
- absorbed country reference는 initiator로 rewrite했을 때 actor와 target이 같아지지 않고 모든 operation 의미가 유지되는 경우에만 rewrite
- rewrite가 불가능하면 authority를 제거하고 invalidation reason 기록
- dissolve에서 명시적 successor로 안전하게 rewrite할 수 있으면 rewrite하고 아니면 제거 후 기록
- source event 삭제 또는 rollback은 atomic snapshot 복원 규칙을 따름

production의 일반 GPT occupation/color effect는 대응 active authority가 없으면 거부한다. 별도 전쟁·외교 시스템을 만들지 않고 현재 turn result가 생성한 검증된 bounded authority만 사용한다.

## 8. 일부 점령·해방·양도

### 8.1 명령과 effect

기존 command/effect envelope와 revision 규칙을 재사용한다. payload는 개별 territory command가 아니라 bounded `territoryIds` 배열을 사용한다.

필수 operation:

- `territory.occupy`
- `territory.liberate`
- `territory.transferOwnership`

각 요청은 actor, target 또는 새 owner/controller, territory ID 배열, authority ID, 기대 revision을 포함한다. 정확한 필드명은 기존 convention에 맞춘다.

planner는 한 command에서 하나의 bounded aggregate effect 또는 기존 batch cap 안의 최소 effect 집합을 만든다. 수천 개 territory를 개별 command/effect로 확장하지 않는다.

### 8.2 검증

- 모든 territory와 country가 존재하며 active인지 검증
- territory ID 배열의 cap, 정렬, 중복 없음 검증
- stale revision과 authority operation/scope/date 검증
- `occupy`: actor가 controller가 되며 owner는 유지
- `liberate`: actor가 authority상 허용되고 현재 controller 관계가 유효해야 하며 controller를 owner로 복원
- owner가 null인 territory에 `liberate`를 적용하면 거부한다. 무주화 명령으로 해석하지 않는다.
- `transferOwnership`: owner를 새 owner로 바꾸고 명시된 정책에 따라 controller도 갱신
- 결과 owner/controller가 6.1의 허용 상태인지 검증
- merge/dissolve와 같은 plan에 포함될 때 최종 state 전체로 reference validity 검증

해방 authority는 actor가 해당 territory를 해방할 수 있는 주체인지와 허용 operation에 `liberate`가 있는지를 모두 확인한다.

### 8.3 projection과 UI

- fill color는 기본적으로 `controllerCountryId ?? ownerCountryId` 국가의 `mapColor`를 사용한다.
- owner와 controller가 다르면 점령 표현을 overlay 또는 pattern으로 구분하되 색상 가독성을 유지한다.
- 게임 기준 국가 경계(P0), 점령선/front, 낮은 zoom에서 숨길 내부 행정선을 분리한다.
- command 결과의 affected territory와 인접 edge만 다시 projection한다.
- 일반 occupation/color update에서 전체 source `setData`, 전체 world serialization, 전체 catalog hash, 전체 projection 재생성을 금지한다.
- 클릭·hover·focus·country panel은 미세 territory에서 현재 국가 의미를 잃지 않아야 한다.
- news와 turn result는 변경된 territory 수와 관련 국가를 표시하되 거대한 ID 목록을 UI 본문에 출력하지 않는다.

## 9. 국가 색상

### 9.1 canonical 값과 migration

- `mapColor`는 `#RRGGBB` uppercase만 허용한다.
- seed의 기존 RGB 외관을 canonical hex로 변환하며 시각적 값이 달라지지 않아야 한다.
- 기존 국가 수, unique color 수, lowercase/noncanonical 수는 14-1 audit에서 실제로 계산한다. 고정 숫자를 성공 조건으로 쓰지 않는다.
- 신규 또는 합병 표시 색상은 결정적 allocator를 사용한다. 고정 6색 palette만 순환하지 않는다.
- 요청된 대표 색상이 있으면 canonicalize하고 contrast/금지값 정책을 통과할 때 사용한다.

예시 요구:

- 소련 재형성에서 `#CC0000` 같은 요청 색상을 적용할 수 있다.
- 오스트리아-헝가리 재형성에서 흰색 계열을 요청할 수 있으나 바다·경계·label과 구분되는 실제 fill/outline 정책을 함께 검증한다.

### 9.2 identity 계승과 색상 변경

합병 국가의 ID와 기존 실제 simulation state는 initiator가 계승한다. 국가 이름과 `mapColor` 변경은 별도 명시된 effect다. 새 3글자 국가를 생성해 기존 국가의 정치·경제·외교를 복제하지 않는다.

### 9.3 command/effect와 authority

`country.changeMapColor` command/effect를 기존 envelope에 추가한다.

- target country, canonical color, authority ID, expected revision 검증
- 일반 GPT result는 active `CountryPresentationAuthority`가 target과 color를 허용해야 함
- merge plan 내부의 명시적 presentation change도 같은 plan에서 생성된 bounded authority 또는 기존 merge용 검증 계약을 통해 승인
- debug는 공통 debug 정책만 사용
- 변경된 country가 owner/controller인 territory만 affected set에 포함
- undo/redo 후 색상과 지도 projection이 정확히 복원

## 10. GPT 계약

GPT 입력에는 전체 catalog 좌표나 수천 개 territory를 기본으로 제공하지 않는다. 서버 측 resolver가 다음 순서로 처리한다.

1. GPT가 country ID, bounded region reference, 의도한 operation을 구조화해 반환
2. strict schema parse
3. resolver가 catalog index로 region reference를 territory ID 집합으로 변환
4. authority scope와 request cap 검증
5. planner가 deterministic effect 작성
6. atomic commit

GPT 출력의 좌표, GeoJSON, polygon, 임의 territory ID는 거부한다. 모호한 region은 확인 가능한 후보로 실패시키며 임의 geometry를 생성하지 않는다.

## 11. 성능과 전달 기준

### 11.1 구조적 hard gate

다음은 환경과 무관하게 실패 조건이다.

- 점령 중 runtime polygon tessellation 발생
- 일반 점령·색상 변경에서 전체 map source `setData` 발생
- camera pan/zoom 중 world serialize, 전체 catalog hash, 전체 projection 재생성 발생
- territory별 개별 command/effect 폭발
- 변경되지 않은 대형 collection의 불필요한 deep clone
- GPT 기본 context에 전체 territory 목록·좌표 포함
- 명백한 UI stall, OOM, 반복할수록 제한 없이 증가하는 heap/feature cache

### 11.2 reference-machine benchmark

FPS, frame time, interaction latency, heap 변화는 hard coded 보편 임계값 대신 reference machine 결과로 기록한다.

- 측정 환경, browser/build mode, catalog version, viewport, scenario를 기록한다.
- 기존 map과 micro-territory map의 pan/zoom 체감 및 측정값을 비교한다.
- 점령 전후 전체 source 재생성이 없는지 계측한다.
- 기존 Playwright/WebGL 제약을 존중해 single worker가 필요하면 그대로 사용한다.
- 명백한 장시간 정지, OOM, 무한 증가, 전체 source 재생성은 실패다.
- 작은 frame-time 편차만으로 schema나 기능 전체를 실패 처리하지 않는다.

특정 CDP 호출 순서, 강제 GC 횟수, worker 조합 전수 검사, 30초 시나리오 3회 반복은 필수로 만들지 않는다. 최소한의 재현 가능한 benchmark를 사용한다.

## 12. 실행 순서, 병렬 구현, 검증 요청 지점

### 12.1 전체 실행 순서

다음 순서를 기본 실행 경로로 사용한다. `REVIEW`에서는 구현을 멈추고 사용자에게 검증을 요청한다. 사용자가 해당 구간을 확인해 진행 가능하다고 판단한 뒤 다음 구간으로 이동한다.

```text
14-1 → 14-2 → REVIEW A
              ↓
        14-3 ∥ 14-4
              ↓
            14-5 → REVIEW B
              ↓
        14-6 → 14-7 → 14-8 → REVIEW C
              ↓
        14-9 → 14-10 → REVIEW D
              ↓
   ┌─ 14-11 → 14-12 → 14-13 → 14-14 → REVIEW E
   └─ 14-15 → 14-16 → 14-17          → REVIEW F
              ↓ 두 구간 모두 승인
        14-18 → 14-19 → 14-20 → REVIEW G
```

| 구간 | 실행할 task | 병렬 여부 | 사용자 검증 시점 |
|---|---|---|---|
| A. 기준선과 원본 결정 | `14-1 → 14-2` | task 내부의 읽기 전용 audit만 병렬 가능 | **14-2 완료 후 REVIEW A** |
| B. schema 계약 | `14-3 ∥ 14-4 → 14-5` | 14-3과 14-4 조건부 병렬 가능 | **14-5 완료 후 REVIEW B** |
| C. immutable catalog | `14-6 → 14-7 → 14-8` | 핵심 생성 단계는 순차 | **14-8 완료 후 REVIEW C** |
| D. consumer와 production cutover | `14-9 → 14-10` | 순차 | **14-10 완료 후 REVIEW D** |
| E. 일부 점령 | `14-11 → 14-12 → 14-13 → 14-14` | 구간 내부는 순차 | **14-14 완료 후 REVIEW E** |
| F. 국가 색상 | `14-15 → 14-16 → 14-17` | 구간 내부는 순차 | **14-17 완료 후 REVIEW F** |
| G. 최종 통합 | `14-18 → 14-19 → 14-20` | 순차 | **14-20 완료 후 REVIEW G** |

### 12.2 병렬 구현 규칙

병렬 실행은 선택 사항이다. 안전한 파일 소유권 분리가 불가능하면 표의 번호 순서대로 순차 실행한다.

1. `14-3`과 `14-4`는 각각 world schema와 simulation schema를 담당하므로 병렬 가능하다.
   - 시작 전에 공통 ID, canonical ordering, atomic pair interface를 고정한다.
   - 두 작업자가 같은 schema registry, barrel export, atomic runtime 파일을 동시에 수정하지 않는다.
   - 공통 파일 연결과 충돌 해결은 `14-5`에서 한 작업자가 수행한다.
2. `14-11~14-14`와 `14-15~14-17`은 `14-10` 승인 후 조건부 병렬 가능하다.
   - occupation lane과 color lane의 domain 파일, 테스트, projection port 소유권을 먼저 분리한다.
   - command union, shared effect registry, world entity, map projection처럼 겹치는 파일은 한 명의 integration owner만 수정한다.
   - 두 lane이 같은 파일을 수정해야 한다면 병렬화를 취소하고 occupation 구간 후 color 구간을 순차 실행한다.
   - `14-18`은 REVIEW E와 REVIEW F가 모두 끝난 뒤 시작한다.
3. `14-6→14-7→14-8`, `14-9→14-10`, `14-18→14-19→14-20`은 결과물이 다음 task의 입력이므로 병렬 실행하지 않는다.
4. production cutover인 `14-10`은 catalog generation이나 schema migration과 병렬 실행하지 않는다.
5. 병렬 작업자는 기존 dirty worktree를 공유해 덮어쓰지 않는다. 별도 worktree 또는 명시적인 파일 소유권을 사용하고, 병합 전에 각 lane의 시작·종료 hash를 확인한다.

### 12.3 사용자 검증 요청 형식

각 REVIEW에서 다음 내용을 한 번에 제시한다.

- 완료한 task 번호와 `pass | fail | blocked` 상태
- 실제 변경 파일과 기존 dirty 파일의 구분
- 실행한 검증 명령, exit code, 핵심 결과
- 화면 검증이 필요한 경우 재현 절차와 screenshot 또는 관찰 결과
- 남은 제한과 다음에 실행할 정확한 task 번호
- 병렬 구간이면 lane별 결과와 공통 파일 충돌 여부

`fail` 또는 `blocked`이면 다음 REVIEW 구간으로 진행하지 않는다. 원인과 재개 조건을 checkpoint 보고서 또는 REVIEW 증거에 남긴다. REVIEW D는 별도 JSON을 추가하지 않고 14-10의 runtime smoke 결과와 14-8 catalog 보고서를 함께 제시한다.

### 12.4 단계별 실행 계획

각 task는 위 의존 관계와 REVIEW 승인을 따라 실행한다. `blocked` 또는 fail이면 원인, 증거, 재개 조건을 현재 checkpoint 보고서에 남기고 후속 production cutover를 수행하지 않는다.

## 13. checkpoint와 재개 규칙

- checkpoint 보고서만 생성한다. 모든 세부 단계마다 형식적인 JSON을 만들지 않는다.
- 각 보고서는 `status: pass | fail | blocked`, 시작 HEAD, baseline 구분, 수행 단계, 실제 명령과 exit code, 핵심 측정값, 변경 파일, 남은 문제, 다음 재개 단계를 포함한다.

## 16. 최종 완료 정의

Prompt 14는 다음을 모두 만족할 때만 완료다.

1. 검증된 실제 행정 polygon으로 immutable micro-territory catalog가 재현 가능하게 생성된다.
2. source lock, stable IDs, topology, render artifact, roots가 build/CI에서 검증된다.
3. server와 browser가 각자 정해진 범위만 검증하고 브라우저가 전 세계 canonical asset을 처리하지 않는다.
4. WorldStateV3와 SimulationStateV2 migration이 strict하고 atomic하며 dual authority가 없다.
5. owner/controller 분리 기반의 일부 점령·해방·양도가 bounded authority 아래 동작한다.
6. 합병 initiator의 CountryId와 실제 기존 simulation state가 계승된다.
7. 국가 색상이 authoritative state이며 요청된 색상과 deterministic fallback을 지원한다.
8. 지도는 affected feature만 갱신하고 pan/zoom 중 불필요한 전체 작업을 하지 않는다.
9. GPT가 좌표나 polygon을 만들지 않는다.
10. refresh 후 2020-01-01 seed로 초기화되고 browser persistence가 없다.
11. 기존 게임 UI와 simulation 기능에 회귀가 없다.
12. 7개 checkpoint 보고서와 최종 검증 결과가 실제 증거와 일치한다.

필수 원본이나 도구가 없어 hard gate를 넘지 못했다면 해당 checkpoint를 `blocked`로 끝내며 Prompt 14 완료로 판정하지 않는다.
