# PROMPT 17 — 기존 게임 오류 수정·실패 복구·개발 잔재 정리

작성 기준: 2026-10-29, D:\gen.
분석 기준 commit: c7eb273198925d5f12ce1b0946174e86f1e3f0f4.

이 문서는 Prompt 16으로 연결한 현재 게임의 오류를 수정하는 실행 프롬프트다. 사용자가 프롬프트 작성만 요청했다면 문서만 만들고 구현을 시작하지 않는다. 구현을 요청받으면 아래 범위의 실제 수정과 필요한 확인을 끝낸다.

이번 작업은 현재 기능의 안정화다. 셀 모양 변경, 새 세계 데이터 생성, 대규모 성능 구조 개편은 후속 작업으로 둔다.

- 위 commit은 출발점을 식별하기 위한 기록이다. 최신 사용자 변경을 그 commit으로 reset하거나 덮어쓰지 않는다.

### 17-01. 명령 재시도와 국가 패널 [F01·F02]

주요 위치:

F01 — 명령 실패의 Retry가 시간 진행으로 바뀌는 문제:
- queue, cancel-action, undo, redo 오류와 실제 턴 진행 오류를 구분한다. 명령 실패에 기존 턴 Retry를 보여주지 않는 작은 수정도 허용한다.
- Retry가 실패한 명령 대신 prepare-turn이나 30일 기본 진행을 호출해서는 안 된다. 실제 턴 Retry는 사용자가 선택한 기간·날짜와 정상 진행의 조건을 유지한다.
- 명령 Retry를 제공한다면 서버 적용 후 응답만 유실된 경우를 고려한다. snapshot을 다시 읽어 조정하거나 필요한 최소 operation identity를 사용해 등록 중복·undo/redo 이중 이동을 막는다. stale 검사나 동시 변경 금지를 완화해서 해결하지 않는다.
- 이미 commit한 턴의 응답 유실 복구, 취소, 잠금 해제와 기존 정상 Retry를 유지한다. 오류 상태를 무조건 idle로 돌려 성공처럼 보이게 하지 않는다.

F02 — 열린 패널의 국가가 사라질 때 렌더 오류:
- 새 world에서 활성 대상인지 렌더 시점에 확인한 뒤 국가·외교 projection을 만든다. 렌더 후 effect로 패널을 닫는 것에만 의존하지 않는다.
- 선택 국가, 외교 대상, 현재 simulation의 플레이 국가가 바뀌는 경우도 안전하게 표시한다. 늦게 동기화된 setup store의 이전 ID 때문에 없는 국가를 읽지 않는다.
- 유효하지 않은 국가를 도메인 projection이 거부하는 규칙은 유지한다. 가짜 국가를 만들거나 예외 전체를 삼키지 말고 UI의 대상 선택을 고친다.

필요한 회귀 확인:
- 명령 실패 후 턴 진행 요청이 나가지 않는다. 명령 Retry를 제공하는 경우에는 적용 후 응답 유실에서 효과가 중복되지 않음을 확인한다. Retry를 숨기는 최소 수정이라면 실패 후 read 조정과 턴 Retry 미노출을 확인하면 된다.
- 유효한 작은 도메인 fixture의 병합·해산 후 열린 국가/외교 패널이 오류 없이 닫히거나 유효한 대상으로 바뀐다. undo/redo 이후 화면도 현재 상태를 따른다. 이를 위해 923,443개 전체 셀을 UI 테스트에 넣지 않는다.
- 기존 정상 턴·응답 유실 복구 테스트를 재사용한다. 반복되는 명령별 확인은 작은 매개변수 테스트로 묶는다.

### 17-02. 행동 상한과 종료 기록 [F03·F04]

주요 위치:

F03 — 대기열 128개와 결과 32개의 불일치:
- 이번 작업의 기본 방향은 현재 결과 계약에 맞춰 활성 행동 상한을 32개로 일치시키는 것이다. queued/resolving 같은 활성 상태와 종료 기록 수는 구분한다.
- UI·서버 등록·context·결과 validator가 같은 정책을 사용하게 한다. UI에서만 막지 말고 서버도 상태를 변경하기 전에 명확한 오류로 거부한다.
- 결과 상한을 128개로 올리거나 자동 다중 턴 처리 기능을 새로 만드는 방향으로 확대하지 않는다. provider 호출 후에야 불가능한 요청임을 발견하는 경로를 없앤다.
- 기존 규격의 활성 행동 33~128개 snapshot을 조용히 자르거나 전체 로드 실패로 만들지 않는다. 새 등록은 막되 기존 행동 취소로 32개 이하까지 복구할 수 있는 명시적 호환 처리를 둔다.

F04 — 완료·취소 기록이 평생 등록 한도를 소모하는 문제:
- 활성 대기열과 종료 행동의 보존 기록을 구분한다. 단순 max 값 상향, 종료 행동의 무제한 별도 배열, 종료 기록 전부 삭제는 해결로 인정하지 않는다.
- 필요한 ID·actor·날짜·status·요약과 현재 보존된 사건·보고서의 참조를 어떻게 유지할지 작은 정책으로 정한다. 기존 host history나 요약 구조를 재사용하고 새 영구 저장 시스템을 만들지 않는다.
- 기존 immutable snapshot을 수정하지 않는다. undo가 옛 혼합 대기열을 복원한 뒤에도 과거 취소 기록 때문에 새 등록이 다시 막히지 않아야 한다.
- 저장 형식을 실제로 바꾸는 경우 새 기본 필드나 정규화 때문에 기존 serialized pair의 canonical hash가 달라질 수 있다. 그 경우에만 기존 형식의 원본 hash 검증 후 필요한 변환을 명시적으로 수행한다. 형식을 유지하는 수정에 새 migration 체계를 강제하지 않는다. 기존 seed 파일·승인 hash를 다시 써서 맞추거나 hash 검증을 건너뛰지 않는다.
- eventLog 전체 절단이나 fact/situation/authority 보존 정책 전면 변경으로 확대하지 않는다. sourceEvent 참조를 깨뜨리지 않고 이번 행동 수명 문제를 해결한다. 다른 장기 기록 상한과 전체 undo 저장 구조는 후속 설계 사항으로 보고한다.

필요한 회귀 확인:
- 31/32/33 활성 행동 경계, 취소 후 공간 회복, 예전 초과 대기열의 로드·취소·정상 진행을 작은 입력으로 확인한다.
- 작은 fixture에서 129회 이상의 등록·취소 후 추가 등록이 가능한지 확인한다. 보존 크기 제한은 상한 직전으로 준비한 작은 snapshot의 경계 사례로 확인해도 된다. 운영 상한에 도달할 때까지 수천 회 반복하는 장기 루프는 필수가 아니다.
- 기존 실제 seed pair를 그대로 읽을 수 있고, 옛 혼합 snapshot과 commit→undo→redo→restart에서 필요한 기록·참조와 이전 객체의 불변성이 유지되는지 관련 테스트로 확인한다.
- 이를 위해 전 세계 geometry를 다시 생성하거나 장기 게임 성능 benchmark를 돌릴 필요는 없다.

## 4. 검증 범위 — 필요한 확인만 수행

검증을 별도 개발 프로젝트로 확대하지 않는다. 기본 마무리 범위는 아래 네 가지다.

1. 타입 확인 한 번: node node_modules/typescript/bin/tsc --noEmit --incremental false.
2. 변경한 코드 파일의 lint와 관련 회귀 테스트를 묶어서 실행. F01~F12에 필요한 작은 경계·실패 사례와 기존 commit/undo/redo·응답 유실 검사를 재사용한다.
3. production build 한 번. 17-05의 tracing 확인과 같은 빌드 결과를 사용한다. 실행 중인 dev 서버와 충돌하면 기존 PAX_BUILD_DIST_DIR와 설치 Next 가이드에 따라 출력 하나를 분리한다.
4. 로컬 화면에서 시작·국가 선택·행동 등록·대표 턴·undo/redo의 정상 흐름을 한 번 짧게 확인. 오류 경로는 위 component/fake 응답 회귀로 갈음하며 각각을 브라우저 E2E로 다시 확인할 필요는 없다. 작은 fixture나 기존 scripted provider를 사용한다. 실제 외부 AI 호출은 사용자가 별도로 요청한 경우에만 한다.

다음은 기본 필수 작업이 아니다.
- application 1,433개 전체 또는 전체 E2E를 단계마다 반복 실행하기.
- 전 국가 geometry·247개국 membership 감사, 독립 재생성 byte 비교, 국가별 screenshot.
- 과거 Prompt 15/16의 모든 검사·REVIEW 재수행, 별도 검증 에이전트 승인, 새로운 검증 runner.
- 전체 catalog 재해시, 대용량 negative fixture/세계 데이터 사본, 성능 benchmark·장기 soak test.
- 실제 Codex 작업·Discord/이메일 전송·외부 배포·유료 API 호출.

공용 schema 변경 등으로 실제 영향 범위를 판단하기 어려운 경우에만 기존 전체 테스트를 마무리에 한 번 추가한다. 전체 검사를 관성적으로 반복하거나 무관한 기존 실패를 고치느라 범위를 넓히지 않는다. 이번 변경에서 생긴 실패는 원인을 고치고, 환경상 실행하지 못한 확인은 해당 범위와 이유만 정확히 기록한다.

- 기존 입력·승인 자료를 바꾸지 않고 현재 catalog로 게임을 시작하고 대표 플레이를 이어갈 수 있다.
- 명령 실패가 다른 작업으로 바뀌지 않고, 국가 소멸·세션 초기화 실패·상세 지도 실패가 적절히 복구된다.
- 행동 계약과 보존 정책이 일치하고, 이전 seed/snapshot 및 undo/redo가 필요한 범위에서 호환된다.
- 자동화의 사람 확인 경계와 기존 strict 검증을 유지하면서 재개·종료가 정상 동작한다.
- 관련 확인 결과와 미실행 범위가 사실대로 기록됐다. 모든 향후 성능·데이터 품질 문제가 해결됐다고 보고하지 않는다.

완료 보고는 변경 요약, 실행한 확인, 직접 해볼 조작, 남은 문제만 간단히 작성한다. 앱 전체를 다시 분석한 장문 보고서나 파일별 hash·세션 ID 목록은 필수로 만들지 않는다.

이미 승인된 구현 범위에서는 단계마다 확인 질문을 반복하지 않는다. 장시간 작업 중에는 짧게 진행 상황을 알린다. 기존 사용자 변경을 보존하고 변경은 해당 문제 단위로 정리한다. commit/push는 그 실행 세션에서 받은 사용자 지시를 따른다.
