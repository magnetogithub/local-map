# PROMPT 18 — 지도 렌더링 부하 제거와 실제 플레이 성능 검증

작성 기준: 2026-10-29, D:\gen.
출발점 기록: 6910ce071833ec1fa9ac63848b33a6b21d35bf57 (origin/main 푸시·원격 일치 확인 완료).

이 문서는 Prompt 17 안정화 이후 확인된 심각한 지도 렉을 줄이는 실행 프롬프트다. 프롬프트 작성만 요청받았다면 문서만 작성하고 구현을 시작하지 않는다. 구현을 요청받으면 아래 P0 범위의 수정과 관련 확인을 끝낸다.

목표는 현재 catalog와 게임 의미를 유지하면서 초기 지도 준비·이동·국가 hover/선택 뒤에 쌓이는 큰 작업을 줄이는 것이다. 모든 성능 문제를 한 번에 해결하는 작업으로 확대하지 않는다.

## 1. 출발점과 작업 범위

- AGENTS.md와 현재 git status를 먼저 확인한다. Next 관련 코드를 수정하기 전에 설치된 node_modules/next/dist/docs/의 관련 가이드를 읽는다.
- 위 commit은 출발점 식별 기록이다. 현재 사용자 변경을 reset/checkout으로 덮어쓰지 않는다.
- 추적 가능한 요약은 reports/maintenance/20261029-prompt17-completion-and-performance-summary.json이다. 상세 로컬 분석은 reports/verification/performance-analysis-20261029/result.json에 있다. ignored 상세 보고서가 없어도 관련 코드와 작은 입력으로 계속 진행한다.
- Prompt 17의 Retry 구분, 퇴역 국가 렌더 보호, 행동 상한·기록 보존, 초기화 세션 정리, 상세 오류 복구와 stale 요청 차단을 유지한다. F01~F12를 다시 구현하거나 과거 전체 감사를 반복하지 않는다.
- 이번 핵심은 base front 필터, 희소 front 상태, 빈 상세 source 기록 제거, 색상 캐시와 hover 갱신 축소다. 4절의 소유권에 따라 A 렌더러와 B 색상 계산을 병렬로 진행하되, 같은 지도 consumer를 수정하는 A의 단계는 순차로 진행한다.
- 별도 오케스트레이터·승인 체계·대규모 benchmark runner·검증용 workspace 복제를 만들지 않는다. 이미 수정된 부분은 확인 후 재사용한다.

## 2. 분석에서 확인한 사실과 해석 한계

현재 catalog는 catalog-v3-56fc6c79c216e6bd1a11이며 셀은 923,443개, edge는 3,125,743개다. World V3 + Simulation V2는 의도된 현재 구조다.

기본 zoom 1 타일 네 개만 헤더를 읽은 결과는 다음과 같다.

| 항목 | 값 |

| 고유 edge | 676,904 |
| c=0 해안 | 14,997 |

| c=2 행정 경계 | 4,861 |

- operational-map-consumer.ts의 base front layer에는 filter가 없다. MapLibre의 line bucket은 filter를 통과한 feature의 geometry를 만든다. feature-state opacity를 0으로 두는 것은 이 geometry 생성의 제외 조건이 아니다.
- setFeatureState 호출마다 전체 타일을 다시 파싱한다는 설명은 틀리다. 프레임 요청은 합쳐지지만 대량의 JS 상태 등록과 paint 배열 갱신은 남는다.
- applyCell은 vector source와, 처음에는 비어 있는 exact/changed GeoJSON source 두 개에 동일한 전체 상태를 등록한다.
- visibleCells는 현재 viewport만이 아니라 과거에 관측한 타일의 셀을 계속 포함한다. hover 국가가 바뀌면 이 누적 집합을 복사·순회하며 색상까지 다시 계산한다.
- 신규 map consumer는 delivery의 seen 셀·edge를 다시 전달받는다. 준비 상태나 setup→game에서 map이 재생성되면 큰 작업을 반복할 수 있다. 실제 mount 횟수는 확인이 필요하다.
- 당시 Chrome renderer working set은 최대 약 3.2GiB, Chrome 공유 GPU 프로세스 working set은 약 1.5GiB가 관측됐다. 이는 JS heap 또는 GPU 전용 VRAM 수치가 아니며, 다른 Chrome 탭의 영향도 분리되지 않았다.
- 큰 부하 뒤 후속 idle 측정에서는 CPU가 낮아졌다. 무한 루프나 메모리 누수로 확정하지 않는다. 초기·이동 작업의 적체와 메모리 부담을 먼저 줄인다.
- 676,904→921은 base front 고유 후보의 약 99.86% 감소다. 전체 FPS·GPU 메모리·초기 준비 시간이 그 비율로 개선된다고 주장하지 않는다.

줄 번호나 과거 측정값을 새 합격 기준처럼 고정하지 말고 현재 관련 코드와 실제 결과를 확인한다. 전체 타일·전 국가를 다시 조사할 필요는 없다.

## 3. 반드시 유지할 정확성

- catalog version, cell ID, ordinal, geometry, topology, membership, source identity, 원본 지도와 승인 내용·해시는 바꾸지 않는다. 원본 타일 재생성·수정 없이 진행한다.
- 현재 PBF territory feature의 properties는 비어 있다. ordinal은 국가별 순서가 아니라 셀 hash ID 정렬이다(scripts/prompt15-world-indices.mjs). 국가별 cellCount를 합쳐 247개 연속 ordinal 범위로 색칠하는 step/match 최적화를 적용하면 안 된다.
- owner/controller 구분, 현재 통제국 점령색, null controller, 퇴역 국가, 색 변경, 선택·hover 의미를 유지한다. 현재 상호작용 대상은 owner 우선, controller fallback이다.
- 새 점령·해방·양도·병합과 초기 복원 상태의 전선, 상세 해제, undo/redo, restart가 현재 authoritative world와 일치해야 한다.
- 기존 revision·delta·stale 요청·원자적 commit·실패 후 재동기화 검사를 완화하지 않는다. 이전 world를 최신처럼 표시해서 성능을 맞추지 않는다.
- 현재 PC 화면 높이 보정과 패널 내부 스크롤을 유지한다. 브라우저 확대·모니터 해상도·임시 대형 viewport로 실제 화면의 문제를 숨기지 않는다.

## 4. 작업 분기·합류와 구현 순서

### 4.1 분기와 합류 흐름


| 작업 | 담당 | 선행 작업 | 결과 |
| --- | --- | --- | --- |
| 18-01 | 합류 담당 | 공통 시작 | 같은 조건의 기준 측정, 변경 상태·파일 소유권·공유 함수 계약 확인 |

기준 측정 중에는 A·B가 구현을 바꿔 전후 조건을 섞지 않는다. 병렬 실행 환경이 없으면 같은 소유권과 합류 조건을 유지하며 순차로 수행한다. 분기별 새 저장소·worktree·전체 workspace 사본은 만들 필요가 없다.

합류 담당:
- 18-01 기준 측정과 현재 서버·브라우저 조작을 맡는다. 분기 구현 중 각각 별도 브라우저를 열어 같은 baseline을 반복하거나 사용자의 진행을 덮어쓰지 않는다.

- A·B가 쓰는 operational-map-projection의 기존 인터페이스를 공통 시작에서 확인한다. A는 소비자 기록·hover를, B는 projection 내부 색상 계산을 맡아 중복 캐시·중복 구현을 피한다.
- A·B가 마친 파일만 인계받아 직접 연결되는 차이를 조정한다. 통과한 분기를 처음부터 다시 구현하지 않는다.

공통 운영:
- 소유권은 편집 기준이다. 다른 담당 파일은 읽을 수 있지만 동시에 고치지 않는다. 경계 변경은 담당자끼리 정하고 한 명이 수정한다.
- 각 분기는 자기 코드에 직접 연결되는 작은 검사만 실행하고, 변경 파일·공유 계약 영향·검사 결과·남은 연결 사항을 짧게 전달한다.
- 전체 타입/lint 묶음·production build·실제 전후 성능 비교는 합류 담당이 한 번 모아 수행한다. 같은 build나 전체 회귀를 분기마다 반복하지 않는다.
- 각자의 작은 fixture·임시 경로만 사용하며 다른 분기의 출력이나 사용자 변경을 덮어쓰지 않는다. 공용 테스트 fixture 변경이 필요하면 먼저 소유권을 정한다.
- 분기별 PASS 접수·독립 승인·사용자 확인 대기를 추가하지 않는다. 한 분기의 문제가 독립된 다른 분기를 멈추게 하지 않는다.
- B가 먼저 끝나면 A의 읽기 검토를 도울 수 있다. 파일 담당을 넓혀 새 구현 범위를 추가하지 않는다.

- 주요 파일: src/lib/map/operational-map-consumer.ts, operational-vector-delivery.ts, operational-map-sources.ts, operational-country-labels.ts, src/lib/projection/operational-map-projection.ts, src/components/map/OperationalWorldMap.tsx.

- 도구의 URL·권한 차단을 우회하지 않는다. Chrome 내부 진단 페이지 접근을 필수 관문으로 만들지 않는다.

### 18-02. Base front와 희소 front 상태 [A · 최우선]

operational-map-consumer.ts의 기본 전선 처리부터 줄인다.

- base vector front를 원래 국가 경계 c=1로 제한하는 필터를 적용한다. 정밀·변경 전선 source는 별도로 유지한다.
- 비국경 셀에 새로 생긴 전선과 복원된 전선이 initialIds→incidentEdges→stageDetail 및 updateWorld→stageDetail에서 완전한 geometry로 exactFronts/OPERATIONAL_FRONT_SOURCE_ID에 반영되는지 확인한다.
- 선택 국가 상세를 닫아도 authoritative 변경 전선 source가 사라지지 않아야 한다. 작전·행정 경계나 실제 전선을 단순히 끄는 방식으로 통과시키지 않는다.
- 초기 edge 전체에 front 상태를 미리 기록하는 작업도 줄인다. 기본값을 c=1에 두고 실제 차이가 있는 edge만 override하는 방식을 우선 검토한다.
- source와 다른 owner/controller, null controller를 가진 초기 셀의 incident edge 보정을 유지한다. 예전 국가 경계라도 현재 같은 controller라면 전선이 아니어야 한다.
- 기본값과 override를 합칠 때 명시적 false를 보존한다. 예를 들어 coalesce(feature-state.front, c=1)는 false override를 유지하지만, truthy 검사로 기본 true를 되살리면 안 된다.
- 정확성 경로를 확인하면서 수정한다. 필터 한 줄만 바꾸고 동적·복원 전선 검사를 생략하지 않는다.

### 18-03A. 실제 source 상태와 hover 작업 축소 [A · 18-02 후 순차]

- 비어 있는 exact/changed source에 모든 셀 상태를 선등록하지 않는다. 실제 해당 source에 있는 feature에 필요한 상태만 적용한다.
- 상세 geometry가 나중에 나타날 때 최신 색·점령·선택·hover 상태가 즉시 적용돼야 한다. 상세 해제 후 vector exactCell 마스킹도 올바르게 복원한다.
- 사라진 상세 source feature의 불필요한 상태는 수명에 맞춰 정리할 수 있다. 다른 source에 남아 있는 변경 geometry의 상태를 함께 지우지 않는다.
- paint가 읽지 않는 ID·국가 정보 등을 매번 feature-state payload로 복사할 필요가 있는지 줄인다. authoritative world와 hit 판정은 기존 정체성을 유지한다.
- hover/선택이 바뀔 때 매번 과거 관측 셀 전체를 복사·순회하고 색까지 재계산하는 경로를 없애거나 크게 줄인다. 관련 국가/feature 인덱스와 최소 flag 갱신을 사용한다.
- 같은 hover 값의 반복 갱신은 생략한다. 프레임 단위로 합치거나 작업을 나누는 경우 오래된 hover 결과가 최신 선택·world를 덮어쓰지 않게 한다. 작업량 자체를 줄이지 않은 채 지연만 늘리지 않는다.
- 세션 준비·페이지 전환의 map remount 원인이 보이면 근거와 필요한 작은 보정을 합류 담당에게 전달한다. component 수정은 합류 담당이 인계 후 수행하며, 공통 layout·전역 저장 구조 전면 개편은 선행 조건으로 만들지 않는다.

### 18-03B. 색상 계산 재사용과 캐시 [B · A와 병렬]

- operationalCellView가 mapColorPresentation을 셀마다 반복 계산하지 않도록 projection 내부에서 현재 국가 색상표 또는 작은 유한 캐시를 재사용한다.
- 색 변경·undo/redo·국가 수명 변경과 null controller의 기본 색을 반영한다. 과거 색이나 상태를 계속 붙잡는 무제한 캐시를 만들지 않는다.
- 기존 함수의 검증과 반환 의미는 유지한다. 캐시 hit 때문에 잘못된 ordinal·없는 controller·잘못된 색을 성공으로 처리하지 않는다.
- 작은 fixture에서 반복 호출의 계산 재사용, 색 변경·복원, null controller와 입력 거부를 확인한다. 소비자 전체 테스트를 복사하거나 큰 world를 새로 만들지 않는다.
- A가 담당하는 source별 기록·hover flag 최적화와 중복 구현하지 않는다. 경계가 필요해지면 기존 함수 계약을 먼저 유지하고 합류 시 작은 연결만 조정한다.

### 18-04. 회귀와 실제 플레이 성능 비교 [합류 담당 · A/B 완료 후]

기존 작은 fake map·projection/component 테스트를 재사용한다.

- 기본 c=1 전선, 명시적 false override, null controller, 비-c1 새 전선과 초기 복원 전선을 확인한다.
- 점령→해방/양도→undo/redo에서 색·전선·선택과 기존 exact geometry 의미가 유지되는지 확인한다.
- 빈 source에는 선등록하지 않지만 상세를 열면 상태가 적용되고, 닫으면 기본 지도 마스킹이 복원되는지 확인한다.
- 색 변경과 hover 캐시의 최신성, 같은 hover 반복 생략, source별 상태 기록 수 감소를 작은 입력으로 확인한다. 이를 위해 923,443개 셀을 단위 테스트에 복제하지 않는다.
- 기존 테스트가 기본 전선을 항상 명시적 feature-state로 가정했다면, 기본 렌더 표현식과 override를 합친 실제 의미를 검증하도록 바꾼다. 상태·전선 assertion을 삭제해 녹색으로 만들지 않는다.
- 변경 코드 lint, 관련 회귀, 타입 검사를 묶어 한 번 수행한다. 실패하거나 코드가 다시 바뀐 부분만 필요한 범위에서 재확인한다.
- 마지막에 production build를 한 번 확인한다. 실행 중인 dev 서버와 충돌하면 기존 PAX_BUILD_DIST_DIR와 설치 Next 가이드에 따라 출력 하나를 분리한다. 플랫폼·컨테이너·전체 tracing 매트릭스를 새 관문으로 만들지 않는다.
- 실제 턴 화면은 기존 development scripted provider로 확인하고 production DEBUG 제한은 유지한다. production provider를 시험하려고 실제 AI 턴을 호출하지 않는다.
- 실제 기본 화면에서 시작·국가 선택·행동 등록·1일 진행·undo/redo를 짧게 확인한다. 기존 scripted 동작 예시는 대한민국으로 시작한 뒤 아래 행동이다.

  [DEBUG_WORLD_EFFECT] 북한에 전쟁을 개시하여 휴전선 인근을 점령

- 같은 브라우저 조건에서 초기 준비·안정된 idle·지도 이동·hover/선택의 전후를 비교한다. 구조상 기록 수가 줄었다는 결과와 실제 정지·CPU·메모리 개선을 구분해 보고한다.
- 심각한 기본 지도 정지가 남으면 완료로 포장하지 말고 해당 지도 경로를 더 좁혀 확인한다. 전체 성능이 모두 해결됐다는 표현은 사용하지 않는다.
- 본인이 만든 작은 임시 계측·파일·화면 override만 정리한다. 사용자 서버·탭·자료를 임의로 종료·삭제하지 않는다.

## 5. 이번 범위 밖과 후속 항목

다음은 이미 관찰된 후속 항목이며 이번 P0 완료의 선행 조건이 아니다.

- 선택할 때마다 국가 전체 exact GeoJSON을 파싱하는 경로의 확대 단계별 로딩·선택별 취소·parsed cache 개선.
- Worker 기반 PBF/JSON 변환, 새로운 렌더 속성·GPU lookup 또는 거대 색상 표현식 도입. 원본 hash를 먼저 검증하고 geometry/ID를 보존하는 설계가 필요하므로 별도로 다룬다.
- zoom 이벤트마다 국가 라벨 필터를 다시 설정하는 작업의 임계값 기반 개선.
- 준비 상태·페이지 전환 전체의 map 영속화 구조 재설계.
- 서버의 동일 context 3회 생성, delta 중복 비교, 전선 조회·hash 최적화.
- 클라이언트의 전체 territory dictionary 복사와 영구/chunked 저장 구조 전면 개편.
- 전 세계 geometry·tile 재생성, 셀 크기/모양/ID 변경, 승인 자료 재작성, 보류 국가 재감사, 전체 catalog 재해시.
- 전체 application/E2E 반복, 모든 국가 screenshot, 장기 soak/benchmark, 별도 REVIEW·접수 manifest·사용자 승인 단계.
- 새 게임 기능·새 모델·API 공급자·브라우저 저장·외부 배포.

직접 필요한 작은 인접 보정은 할 수 있지만 위 항목을 한꺼번에 구현하지 않는다. 큰 국가 상세 로딩 등 남은 문제가 있으면 재현과 영향·후속 범위를 명확히 남긴다.

## 6. 완료 기준과 보고

- 기본 전선과 초기 상태 등록의 불필요한 작업이 실제 코드·작은 회귀·관측 수치로 감소했다.
- 현재 world의 점령색·동적 전선·국가 수명·상세 복구·undo/redo가 유지된다.
- 동일한 실제 브라우저 조건에서 기본 지도 준비·이동·hover 후의 심각한 정지가 완화됐고, 남은 지연의 범위가 구분됐다.
- 원본 데이터·승인 hash와 production DEBUG 제한을 보존했으며 외부 AI를 호출하지 않았다.
- 변경 위치, 실행한 관련 검사, 전후 측정 조건·수치, 직접 해볼 조작과 남은 문제를 간단히 보고한다. 기능 검사 통과를 성능 증거로 대신하지 않는다.

긴 작업 중에는 현재 확인한 병목과 다음 확인을 짧게 알린다. 승인된 구현 범위에서 단계별 확인 질문을 반복하지 않는다. commit/push는 그 구현 실행에서 받은 사용자 지시를 따른다.
